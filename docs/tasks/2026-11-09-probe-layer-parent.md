## 二、这不是界面缺陷，是判据拿错了参照物

暴雪的层号**每嵌一层加 1**：窗口 1 → 窗口里的滚动区 2 → 滚动区里的正文 3。
现在的代码（[Probe.lua:3128](../../GoldQuestLedger/Probe.lua)）把**每一颗子孙**都拿去和**窗口主帧**的层号比：

```lua
elseif winLevel and l > winLevel + 1 then
```

于是凡是住在两三层里的控件，天生就是"越界 +2/+3"。126 / 43 / 3 三条清单量出来的全是正常嵌套。

后果不是难看，是**仪器把信号埋掉了**：
- `LIST_CAP = 20` 只列前 20 条，真出现一颗 510 那一类的，会被 126 条正常嵌套挤到看不见；
- 报告越长，他下次复测就越挑不出要看的那一行。

### 离线实测（本轮量化，`tests/_tmp_depth.py` 一次性脚本，用完删）

三扇窗都建出来后按真实 `__children` 递归摊树：

| 窗口 | 主帧层号 | 子孙颗数 | 树深分布 | 和**直接父帧**比，最大差 | 父差 >1 的颗数 |
|---|---|---|---|---|---|
| 矩阵 | 101 | 31 | 第1层9 / 第2层7 / 第3层12 / 第4层3 | **+0** | 0 |
| 设置窗 | 111 | 28 | 第1层5 / 第2层1 / 第3层15 / 第4层7 | **+0** | 0 |
| 日志窗 | 1 | 6 | 第1层5 / 第2层1 | **+1** | 0 |

日志窗那个 `+1` 就是 ×（本轮修完的 `parent:GetFrameLevel() + 1`），它正好卡在允许线上。
⇒ **换成"和直接父帧比"，今天三扇窗就是干净的**，不需要再改任何界面。

深度这一列也顺手回答了另一件事：离线树到第 4 层，而他实机那份设置窗写着"截在 4 层上限，下面还有没扫的"
⇒ 真客户端的设置窗比离线树更深，4 层上限在实机上有盲区。

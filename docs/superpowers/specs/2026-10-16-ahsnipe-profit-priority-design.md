# AHSnipe 队首改按整单利润排序 设计（第二十三轮）

**Goal:** 队首不再是"刚扫到的最新鲜一条"，而是"新鲜闸门内整单利润最大的一条"，让突然出现的大单
抢在剩余鱼饵前面，同时保留过期数据不能挤占队首的保护。

**用户诉求原话**：「时间新鲜度是优先级队首，还需要考虑整单利润大小」「大单肯定应该是队首，
目前的逻辑似乎剩下的鱼饵是队首」。口径已确认：**用现成字段算门槛差**（不给 Scanner 加市场价字段）。

## 全局约束

- 排序只做"选哪条先买"，不改显示粒度（仍是一行一个单价档位）、不改购买粒度（仍是一次点击把
  该件全部低于门槛档位合并成一个请求）、不改购买 API 发送时机纪律（必须在硬件点击栈内直调）。
- 不引入新数据字段：利润只用行上已有的 `threshold`/`unitPrice`/`quantity`。
- 每次排序的计算量必须与行数同阶（≤60 行），不在渲染循环里做额外遍历。

## 利润定义

`RowProfit(row) = max(0, (row.threshold - row.unitPrice)) * row.quantity`（铜币）

- `threshold` 是扫描时按主簇最低价 ×折扣算出的**下单限价**，所有入列档位都 ≤ 门槛，所以差值非负。
- 语义是"这一档买下来相对限价还剩多少安全垫 × 数量"，不是到手利润——这是用户选的口径，
  代价与收益都写在下面"取舍"。
- 缺 `threshold` 或 `quantity` 的行按 0 计（不会因此被抬到队首）。

**合并感知**：一次点击吃掉的是该件**全部**新鲜档位，所以排序键取"该件参与合并的那些行的利润合计"，
而不是被点那一行自己的利润。非 commodity 一行就是一枪，用本行利润。

## 新鲜度闸门

`FRESH_GATE = 20`（秒）：`GetTime() - row.seenAt <= 20` 才算新鲜。

- 新鲜行之间按利润降序；**任何新鲜行都排在过期行之前**；过期行之间保持旧行为（`seenAt` 降序、
  同次命中按单价升序）。
- 20 秒的依据：节流闸门约 1 查询/秒，监控 8 件整轮 8~9 秒（见记忆
  [[project-ahsnipe-scan-latency-findings]]），20 秒 ≈ 两轮多没被刷新才降级，不至于把
  还在聚焦复查的正常数据判死。
- 为什么必须留闸门：利润来自快照，快照过期就是第二十一轮"连点四次均价否决"的病根
  ——一条过期的假大单占住队首，等于把整条购买通道（报价 3s／成交 10s 独占）锁死在必然失败上。

## 排序键全序

1. 新鲜（闸门内）优先于过期；
2. 都新鲜：合并利润降序；
3. 利润相同：`seenAt` 降序（新数据优先）；
4. 同一次命中的多行：`unitPrice` 升序 → 连点先买最便宜档；
5. 仍相同：`quantity` 升序。

`List.NewerThan` 保留为**过期桶内部**的比较器（第 3~5 键与它一致），不删。

## 60 行上限的淘汰口径

改为按 `seenAt` **最旧**淘汰，而不是"排序末尾"。

原因：排序末尾现在可能是"新鲜但利润低"的行，继续按队尾淘汰会把还能买的活数据挤掉、
把过期数据留在列表里，跟本轮目标正好相反。淘汰仍是 O(n) 一次线性找最小 `seenAt`。

## UI：按钮上带预估利润

**不加第五列**（窗口 430 宽、内容帧 392、滚动条占右 26，`总价` 从 300 起只剩约 100px，
塞第五列必须整体加宽并给每行多建一个字体串——为了一个"看得懂为什么排第一"的辅助信息不值当，
也违背最小改动偏好 [[feedback-minimal-click-ui]]）。

改为在底部按钮文案上给出这次点击的收获：`立即购买  +12.34g`（数字 = 队首行的合并利润，
coin 串去掉"g"歧义直接用 `GetCoinTextureString`），忙时仍是 `购买中…`。
理由：一次点击吃掉的是该件全部档位，按钮上的数正好等于这一枪的预期安全垫，
比逐行显示"档位利润"更贴合实际操作。行内不显示利润，列表布局完全不变。

## 取舍（写清楚，便于事后复盘）

- **门槛差 ≠ 到手利润**：门槛本身是主簇最低价乘折扣，所以同一件物品里"单价越接近门槛"的档
  利润趋近 0，而"深折扣"的档排前——这正是我们想要的排序方向。但跨物品比较时，折扣系数不同的
  物品之间会失真（门槛低的商品安全垫天然薄）。用户选择先用现成字段试，实测不满意再加市场价字段。
- **不做"利润/秒"之类的性价比排序**，本轮只换排序键。
- **不做行内按钮、不做多键位排序切换**（遵守 [[feedback-minimal-click-ui]]）。

## 测试

- `test_profit_ranking`：两条都新鲜，利润大的抢队首；利润相同按 `seenAt`；缺 `threshold` 的按 0 计不误抬。
- `test_profit_fresh_gate`：利润最大但 `seenAt` 超过 20 秒的行排在新鲜小单之后；继续推进 `now` 后
  新鲜行也降级时，过期桶仍按 `seenAt` 降序。
- `test_profit_merged_key`：同一物品两档（点击会合并）→ 用该件合计利润参与排序，
  单档利润虽小但合计最大的那件应抢队首。
- `test_row_cap`（改）：61 行入列 → 淘汰 `seenAt` 最旧的一行，且淘汰者不依赖于它当前排在第几位。
- `test_snipe_list_buy` 追加按钮文案断言：有队首时文案含 `立即购买` 与 `+`，忙时仍是 `购买中…`。
- 现有断言里"队首=最新鲜"的口径逐条复核：`test_snipe_list`、`test_row_reconcile`、`test_merge_request`、
  `test_buy_outcome_deletes_row`、`test_snipe_list_buy`、smoke 与 scanner 流程测试里所有 `GetFront()`，
  按新模型改成显式声明理由的断言，不靠巧合通过。

排序时机：只在 `Add`/`DropRow`/`MarkGone`/`Render`/购买结局这些事件上重算（`GetTime()` 取当下），
没有计时器主动重排——所以"数据过期自动降级"发生在下一次扫描有动静时，这与扫描每 8~9 秒必然
触发一次 `Add` 的现状吻合，不必为排序单独加计时器（加也不该发购买消息，见硬约束）。

门禁：`PYTHONIOENCODING=utf-8 python tests/run_tests.py --syntax` 全绿。

## 验收（游戏内）

1. 造一条大单（数量多、离门槛远）+ 一条小鱼饵，都在 20 秒内 → 队首是大单，按钮文案的 `+…g` 跟着变大。
2. 让大单过期（停止扫描它 20 秒以上，别的不受影响）→ 它掉到新鲜行后面，列表不会点不动。
3. 同一物品两档 → 点一次仍是合并一枪（第二十二轮行为不变），两行一起出门。
4. 行数超 60 → 出门的是最旧那条，不是利润最低那条。
5. `/ahsnipe log` 的 `点击购买 …` 行带利润，方便事后核对"为什么点它"。
